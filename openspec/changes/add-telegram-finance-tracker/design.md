## Context

См. proposal.md для мотивации. Python-пакет содержит пустые точки запуска и конфигурацию, каталоги bot/handlers, db и analytics. Объявлены aiogram и SQLAlchemy. Моделей и работающих обработчиков нет. Дизайн нужен из-за новой модели данных и взаимодействия нескольких модулей.

## Goals / Non-Goals

**Goals:** минимальный запускаемый бот, сохранение точных данных, простые границы Telegram-диалога и постоянного хранилища, возможность отдельно добавить аналитику.

**Non-Goals:** универсальные репозитории, дополнительные сервисы, очередь задач, постоянные черновики и подключение аналитических библиотек.

## Decisions

### Запуск и структура

Один процесс с long polling aiogram. Обработчики и FSM остаются в bot, модели и конкретные операции хранения — в db. Конфигурация содержит токен бота и путь SQLite. Реализовать существующий entry point fin_tracker:main и запуск через python -m fin_tracker. HTTP-сервер и webhooks для локального запуска не требуются.

### Модель данных

- users: UUID первичный ключ, уникальный telegram_id.
- transactions: UUID, user_id, kind (income/expense), amount_kopecks TEXT, occurred_at (UTC), nullable comment.
- tags: UUID, user_id, name, normalized_name, is_archived; UNIQUE(user_id, normalized_name).
- transaction_tags: составной первичный ключ (transaction_id, tag_id), внешние ключи.

Удаление операции удаляет только её связи; удаление тега меняет is_archived. Переименование не копирует название в транзакции, поэтому история автоматически показывает актуальное имя. Нормализация: strip и casefold; внутренние пробелы сохраняются. При восстановлении сохраняется прежнее написание имени.

Все операции хранения принимают владельца, ограничивают запросы его user_id и проверяют владельца каждого назначаемого тега, включая поддельные callback ID. SQLite foreign_keys включается для каждого соединения. Составной ключ исключает повторное назначение одного тега.

### Точные суммы без бизнес-максимума

Разбор по формату [0-9]+([.,][0-9]{1,2})?, без float. Дробная часть дополняется справа нулём; каноническое количество копеек хранится десятичной строкой без ведущих нулей. Нулевая сумма отклоняется.

SQLite INTEGER ограничен 64 битами; REAL теряет точность. TEXT сохраняет требование без искусственного денежного максимума. Расчёты выполняются Python int; SQL SUM над этим столбцом не используется. Вход ограничен только фактическим размером сообщения Telegram, что укладывается в стандартный лимит преобразования int в Python для одного текстового сообщения. Выборки возвращают int копеек для будущей аналитики.

### Диалог и транзакции БД

FSM хранит текущий ввод в памяти: тип, сумму, выбранные теги, комментарий и время начала. Переходы: выбор типа → сумма → теги → комментарий → сохранение. «Далее» на последнем шаге завершает ввод; отдельный экран подтверждения не обязателен. Ошибка суммы оставляет пользователя на том же шаге. «Назад» не сбрасывает значения. «Отменить» очищает состояние.

occurred_at фиксируется один раз при инициировании новой операции пользователем. Для команды-сообщения используется дата этой команды в UTC. Для callback начала используется время получения действия ботом в UTC как доступное приближение момента нажатия: дата сообщения с кнопкой может относиться к старому меню и не используется. Отображение и календарные фильтры используют ZoneInfo('Europe/Moscow'). Последующий ввод, возврат к выбору типа в том же диалоге, сохранение и редактирование сохраняют occurred_at.

Транзакция SQLite открывается только на короткое сохранение или изменение операции и связей. Удерживать её во время пользовательского диалога нельзя. После перезапуска незавершённые состояния отсутствуют. Каждый новый диалог получает уникальный идентификатор, который не переиспользуется после перезапуска; кнопки ввода привязаны к нему. При явном начале новой операции предыдущее состояние сбрасывается с уведомлением и фиксируется новое время начала. Обработка действий одного пользователя последовательна: перед действием проверяется актуальность диалога, после успешного сохранения состояние очищается до обработки следующего действия. Старые кнопки не изменяют текущий диалог; повторное завершение не создаёт дубликаты и не применяет редактирование повторно.

На шаге комментария новый текст заменяет значение в FSM; «Далее» завершает ввод с текущим значением. Кнопка «Очистить комментарий» устанавливает в FSM null и оставляет пользователя на шаге комментария. Это поведение одинаково для создания и редактирования. Запись в БД меняется только при завершении; отмена редактирования сохраняет исходный комментарий.

### Редактирование и архивные теги

Исходная запись остаётся неизменной до завершения редактирования. Архивные теги загружаются как уже выбранные, но не доступны для нового назначения. Снятие сопровождается предупреждением. На сохранении проверяется актуальный статус новых назначений: тег мог быть архивирован в другом диалоге. Архивный тег разрешено сохранить только если он присутствовал в исходной операции и не был снят в текущем вводе.

### SQLite и доступ к аналитике

Использовать синхронный SQLAlchemy и стандартный sqlite3, чтобы не добавлять aiosqlite. Короткие операции БД выполнять вне event loop через asyncio.to_thread; каждая операция создаёт собственную Session. Не передавать Session или ленивые ORM-объекты между потоками, возвращать простые данные.

Выборки используют пользователя, интервал [начало, конец), тип и EXISTS по тегам, исключая дублирование строк. При нескольких тегах применяется логическое ИЛИ. Каталог отчётов, кнопка аналитических запросов и конкретные расчёты добавляются отдельным изменением после решений напарника.

### Процесс реализации и приёмки

Для текущего изменения обязателен процесс из specs/delivery-verification/spec.md: apply (с тестами) → verify → archive. Это дополнительный обязательный этап процесса, а не утверждение о наличии встроенной команды sdd verify. Если такой команды нет, оркестратор назначает отдельному субагенту verify с теми же критериями и отчётом; пропускать этап нельзя.

В apply роли разделены: автор кода приложения и отдельный автор всех тестов. Unit-тесты добавляются по мере появления минимальных функциональных фрагментов, интеграционные — при соединении двух модулей, e2e — после работающего MVP. Автор кода может запускать тесты, но не менять их или настройки для ослабления проверок. Запросы изменений тестов проходят через решение оркестратора и передаются тестировщику с обоснованием.

Автоматизированные e2e используют реальные обработчики, FSM и временную SQLite базу; подменяется только внешняя граница Telegram API. Это позволяет воспроизводимо запускать full-gate без токена. Реальное взаимодействие с Telegram проверяет пользователь при обязательной ручной приёмке.

В apply документируются инструменты и единая команда full-gate, включающая строгую валидацию OpenSpec, синтаксические и статические проверки, все unit/integration/e2e-тесты. Verify отдельно запускает весь gate и сохраняет verification.md с версией, командами, результатами, соответствием сценариев тестам и статусом пользовательской приёмки. После исправлений gate повторяется. Archive доступен только после успешных проверок и явного подтверждения пользователя; отсутствие токена или ответа не снимает это условие.

## Risks / Trade-offs

- TEXT для суммы исключает точный SQL SUM → считать Python int; учитывать это при разработке аналитики.
- SQLite обслуживает одного писателя → короткие транзакции и один процесс первой версии; переход к иной СУБД при реальной необходимости.
- Состояние в памяти теряется при перезапуске → это согласованное поведение, незавершённые данные не записывать.
- Старая клавиатура или параллельные действия могут повторить сохранение → привязывать действия к текущему диалогу, последовательно обрабатывать действия пользователя и очищать состояние после успеха.

## Migration Plan

При первом запуске создавать таблицы в новой SQLite базе. Реальных пользовательских данных и миграций существующей схемы пока нет; framework миграций не добавлять. Документировать запуск, переменные окружения и резервное копирование файла базы при остановленном боте. Перед будущими изменениями схемы подготовить отдельную миграцию. Не удалять базу при откате кода.
