# Журнал оркестрации

## Границы ролей

- Оркестратор `/root`: читает спецификации, назначает этапы, контролирует доказательства, решает Change Request и отмечает tasks.md. Не меняет тесты.
- Apply `/root/implementation`: единственный автор кода приложения, конфигурации запуска и README. Тесты, фикстуры, ожидаемые результаты и настройки проверок запрещены. Может читать и запускать тесты.
- Apply `/root/tester`: единственный автор тестов, фикстур, настроек проверок и full-gate. Не пишет код приложения.
- Verify: будет назначен отдельному субагенту после завершения apply. Не меняет приложение или тесты; возвращает дефекты соответствующей роли.
- Archive: будет назначен отдельному субагенту только после явной пользовательской приёмки актуальной проверенной версии.

## Порядок apply

1. Автор приложения реализует только суммы/нормализацию. Тестировщик добавляет и выполняет unit-тесты. Следующий блок разрешает оркестратор после результата.
2. Хранилище и его интеграционные проверки на временной SQLite.
3. Бот/FSM, unit-проверки состояния и интеграция bot ↔ db.
4. Работающий MVP и e2e через реальные Dispatcher/FSM/SQLite с подменой внешнего Telegram API.
5. Сопоставление всех функциональных сценариев, полный gate в apply; затем отдельный verify.

## Change Request

Автор приложения передаёт оркестратору требование, фактическое/ожидаемое поведение и обоснование. Только после решения оркестратора запрос передаётся тестировщику. Соответствующие спецификации тесты не ослабляются ради реализации.
